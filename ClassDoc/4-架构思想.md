# 适配 Vibe Coding 的软件工程架构思想
先明确：**Vibe Coding（氛围式编程）核心特征**
快速原型、迭代试错、低前期设计成本、边写边调整、高频重构、单人/小团队、追求快速可运行、不堆砌过度抽象、人机协同（AI辅助编码），排斥重型前置建模、复杂分层硬约束、大量接口契约先行。
下面按适配度从高到低整理架构思想，附适用场景、Vibe 优势、落地要点。

## 一、最高适配：轻量化、迭代友好、低前期负担架构
### 1. 单体极简架构（Minimal Monolith）
- 核心思想：所有代码打包单一应用，无分布式拆分，只做基础模块划分，拒绝过早微服务。
- 适配Vibe理由：
  不用处理服务通信、注册中心、分布式事务，改代码立刻运行；AI可以一次性读懂全项目上下文，快速补全逻辑。
- 落地规则：
  仅按业务文件夹分层（api/service/model），不搞多层防腐、DTO过度拆分；原型阶段直接复用实体，不做多层转换。
- 适用：工具脚本、内部后台、SaaS MVP、AI应用、本地工具链。

### 2. 功能模块化架构（Feature-First / 特性驱动模块化）
- 核心思想：按业务功能划分目录，而非技术分层；一个特性一套路由、逻辑、数据模型，高内聚低耦合。
  目录示例：
  ```
  features/
    chat/
      chat_api.py
      chat_logic.py
      chat_schema.py
    agent/
  ```
- Vibe优势：新增功能直接新建文件夹，不改动全局结构；迭代新增需求不用跨多层文件跳转，AI定位修改范围极快；随时可单独抽离模块为独立服务。
- 适配场景：LLM Agent、Web后台、自动化工具、本地桌面应用。

### 3. 管道过滤器架构（Pipeline & Filter）
- 核心：数据流串行处理，每个模块只做单一转换，输入输出标准化（文本/JSON/数据流）。
  例：用户输入 → 提示词模板过滤器 → LLM调用过滤器 → 结果格式化过滤器 → 持久化。
- Vibe优势：新增/删除步骤完全隔离，修改单个Filter不影响整条链路；AI可独立重写任意环节，调试简单；极易做本地测试。
- 典型：RAG、AI工作流、数据清洗、批量脚本、音视频处理。

### 4. 事件驱动极简版（Local Event Bus，进程内事件）
- 区别重型分布式事件：只用内存本地总线，无MQ、无持久化。
- 思想：模块之间不直接调用，发布/订阅事件解耦。
- Vibe优势：新增业务逻辑只需新增订阅器，不用修改原有调用代码；快速插拔功能，适合不断叠加AI能力（聊天、工具调用、记忆、日志）。
- 避坑：不落地分布式消息队列，仅进程内使用。







# 不适合 Vibe Coding 的架构思想

不适合Vibe Coding的地方就是适合人的地方

### 1. 标准微服务架构（多独立部署服务）

- 架构特征：按业务拆独立进程服务、服务注册发现、网关、远程 RPC、分布式事务、多库分库、独立部署流水线
- 不匹配原因：
  1. 前期要定义大量接口契约、DTO、通信协议，写代码前一半时间在设计，违背 vibe 快速上手；
  2. 本地调试需要启动一堆中间件（Nacos/consul、网关、数据库多实例），改一行代码要重启一堆服务；
  3. AI 无法一次性看懂全链路上下文，跨服务排错、修改极繁琐；
  4. 微小需求改动要同步修改多个服务、同步发布，迭代速度腰斩。
- 适用时机：项目规模、并发、团队扩张后再拆分，**绝对不能开局微服务**。

### 2. 完整云原生分布式架构（Service Mesh、多集群、容器复杂编排）

大量基础设施前置约束，编码前要搞定网络、流量、观测、权限，完全背离 “快速写代码验证想法”。
