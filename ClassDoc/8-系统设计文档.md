## 1. 设计目标与约束

### 1.1 设计目标

| 目标 | 说明 |
|------|------|
| 对齐功能基线 | 仅覆盖 SRS 功能需求；非功能/数据安全专项不设硬性设计承诺 |
| 小团队可交付 | 适配约 前端1 + 后端1 + Agent后端1（组长）+ 产品1 + 测试兼职 |
| 低前期基建成本 | MVP 单体可运行；拒绝开局微服务 / K8s / 重型中间件 |
| AI 能力可替换 | LLM / ASR 通过适配层接入，支持云 API 与后续本地/切换模型 |
| 分期演进 | MVP → 二期话术/标签 → 三期客服/日程，目录按 Feature 可增量 |

### 1.2 硬约束（来自需求）

- AI **只建议、不代发**；界面标注「AI 建议」
- 画像 / 标签 / 日程建议默认**草稿**，人工确认后生效
- 客服记录按「沟通摘要」理解，非完整客服工单系统对接（见 `firstMeeting_note`）
- 采纳埋点需可统计（复制次数或采纳事件落库）
- 开发期可用**模拟企微沟通 + 模拟订单**降低联调阻塞

### 1.3 明确不做（设计层）

| 不做项 | 原因 |
|--------|------|
| 微服务拆分、服务网格 | 成本高、小团队运维不可承受；与架构思想冲突 |
| 数据安全专项（加密体系、审计平台、等保） | 客户未要求，避免自埋坑 |
| 性能 SLA 专项设计与压测门禁 | 非功能无硬性要求 |
| 开局自建向量库 / 微调私有大模型机房 | MVP 成本过高；二期按效果再评估 |
| 自动外呼 / 群发 / 代发消息 | 产品原则禁止 |

## 2. 技术选型与成本可行性

### 2.1 选型结论（推荐）

| 层级 | 选型 | 备选 | 决策理由 |
|------|------|------|----------|
| 侧边栏 H5 | **Vue 3 + TypeScript**（已定） | — | 单页、轻量；1 名前端可兼顾后台 |
| 管理后台 | **Vue 3** + 中后台模板（如 Naive UI / Element Plus） | — | **一套 Vue 栈**降学习与组件成本 |
| 业务后端 | Python **FastAPI** 单体 | NestJS | 与 Agent/LLM 生态契合；Agent 组长可主导 AI 管道 |
| AI 编排 | 进程内 Pipeline（函数链 / 轻量 LangGraph 可选） | 独立 AI 微服务 | MVP 同进程；后期再拆 |
| LLM | **DeepSeek 云 API**（OpenAI 兼容协议；密钥 `DEEPSEEK_API_KEY`） | 其他兼容供应商 / 本地 GPU | 见 §2.2；Gateway 可切换模型名 |
| ASR | 云厂商按量转写（二期/三期启用） | 本地 Whisper | 按调用付费，无试听期沉没成本 |
| 主库 | **PostgreSQL** | MySQL | JSON 字段适合画像草稿；生态成熟 |
| 缓存 | MVP **可不引入 Redis**；二期按需 | 一上来 Redis+MQ | 少运维组件 |
| 实时 | **SSE**（SRS 明确） | WebSocket | 实现简单、单向推送足够 |
| 部署 | 单机 Docker Compose（API + PG + Nginx） | K8s | 300 顾问规模足够；成本最低 |
| 对象存储 | 可选 OSS（语音临时文件） | 本地盘 | 三期 ASR 再引入 |

### 2.2 LLM：云 API vs 本地部署（成本关键决策）

| 维度 | 云端 LLM API（推荐 MVP） | 本地部署开源模型 |
|------|-------------------------|------------------|
| 启动成本 | 几乎为 0（按 Token） | GPU 服务器采购/租用，数万～数十万/年 |
| 运维 | 供应商负责 | 需专职运维与显存调度 |
| 效果 | 商用模型开箱较好；可用客户话术做 Prompt/Few-shot | 需调优，小团队难在 MVP 窗口内追平 |
| 切换能力 | 适配层切换模型/厂商 | 绑定硬件与镜像 |
| 数据顾虑 | 走供应商协议；**本期不做出境/合规专项验收** | 数据不出域，但客户未要求此项 |
| 适合阶段 | MVP～试运行～全量初期 | 量大且客户强制数据不出域时再评估 |

**结论（已定）**：默认 **DeepSeek 云 API + 模型适配层（Model Gateway）**；认证读取环境变量 `DEEPSEEK_API_KEY`（OpenAI 兼容 `/v1/chat/completions`）。可通过配置切换 `LLM_MODEL`（如 `deepseek-chat`）；本地部署列为**可选演进**，不进入 MVP 预算。

### 2.3 粗算成本结构（量级，供评审，非报价）

> 以下为技术侧量级估计，便于可行性讨论；正式商务报价另出。

| 成本项 | MVP（约 2 月） | 二～三期累计至试运行 | 说明 |
|--------|----------------|----------------------|------|
| 研发人力 | 3 开发 + 产品为主 | 同团队延续 | 最大成本项 |
| 云主机（2～4 核 / 8～16G） | 低（数百～千元/月级） | 略升 | Docker Compose 单机 |
| PostgreSQL | 同机或托管基础版 | 同左 | 避免一上来高可用集群 |
| LLM Token | 中（随调用量） | 升 | Prompt 控制上下文长度；缓存已确认画像 |
| ASR | 近 0 | 按条计费 | 仅语音消息触发 |
| 企微相关 | 应用配置人力 | — | 依赖客户企业微信能力与权限 |
| 不做项节省 | 显著 | — | 无 K8s、无安全专项、无自建机房 GPU |

**成本控制要点**：

1. 模拟数据先行，避免企微/订单接口阻塞烧人天  
2. 画像确认后结果缓存，减少重复 LLM 调用  
3. 二期话术优先「Prompt + 场景模板 + 客户提供话术库」；向量 RAG 仅在效果不足时加  
4. 看板指标 SQL 聚合，不上独立大数据栈  

### 2.4 技术可行性结论

| 能力 | 可行性 | 主要风险 | 缓解 |
|------|--------|----------|------|
| 企微侧边栏 H5 | 高 | 客户侧应用权限/可信域名 | 行动项先行；开发期 Mock 会话上下文 |
| 画像草稿确认 | 高 | 抽取质量 | 人机确认兜底；置信度+来源展示 |
| SSE | 高 | 代理缓冲 | Nginx 关闭 buffering；断线前端重连（尽力，非 SLA） |
| 销售话术建议 | 中高 | 垂直话术风格 | 客户提供场景与样本；采纳反馈迭代 Prompt |
| 标签推荐 | 中高 | 标签体系不稳定 | MVP 先手工标签；二期再 AI |
| 日程+日历同步 | 中 | 企微日历 API 权限与字段 | 三期做；先站内待办，日历同步可降级为可选 |
| 300 顾问全量 | 中高（单体） | 峰值 LLM 费用与限流 | 队列化异步生成；限并发；缓存 |

### 3.2 架构风格组合

| 风格 | 用法 |
|------|------|
| Minimal Monolith | 单一后端进程，统一部署 |
| Feature-First | `features/profile|reply|tag|schedule|admin|wecom` |
| Pipeline & Filter | AI：装载上下文 → Prompt → LLM → 校验/结构化 → 落草稿 |
| 进程内事件（可选） | `profile.draft_updated` → 通知 SSE Hub；不上 MQ |
| 分层（轻） | api → service → repository；不强制完整 Clean Architecture |

## 4. 模块设计

### 4.1 模块职责与分期

| 模块 | 职责 | MVP | 二期 | 三期 |
|------|------|:---:|:---:|:---:|
| wecom | 企微登录态、外部联系人上下文、日历同步 | 基础鉴权+上下文（可 Mock） | 消息增量 | 日历 |
| profile | 多源装载、画像生成、草稿/确认、字段编辑 | ✓ | 优化 | 优化 |
| reply | 销售/客服话术建议、采纳埋点 | — | 销售+埋点 | 客服+ASR |
| tag | 标签体系 CRUD、客户打标、AI 推荐 | 体系+手工打标 | AI 推荐 | SOP 展示增强 |
| schedule | 时间意图、待办、提醒偏好、日历 | — | — | ✓ |
| admin | 员工组织、角色范围、客户/订单、看板 | ✓ | 采纳率报表 | 增强 |
| ai | Model Gateway、Pipeline、Prompt 管理 | 画像管道 | 话术/标签管道 | 日程/ASR |
| mock | 模拟会话、模拟订单 | ✓（默认开） | 可关 | 可关 |

### 4.2 画像模块（MVP 核心）

**流程**：

```
触发（打开侧边栏 / 手动刷新 / 新消息Mock）
  → LoadContext（客户、已确认画像、近 N 条聊天、订单摘要、客服摘要）
  → BuildPrompt
  → LLM.structured_output（四分区 JSON + confidence + sources）
  → 与已确认字段合并（已确认字段不覆盖，仅写入 draft 增量）
  → 落库 profile_draft
  → SSE 推送 sidebar
顾问确认字段/全部 → 写入 profile_confirmed → 可被统计与后续 Prompt 使用
```

**关键规则**：

- `draft` 与 `confirmed` 分离存储或同表版本+状态  
- 统计看板默认只用 `confirmed`  
- 来源字段：`chat|order|cs_summary|manual`  

### 4.3 回复建议模块（二期）

```
家长消息（文本 / ASR 文本）+ 已确认画像 + 场景(销售/客服) + 学段
  → 检索话术模板（DB 场景表；可选后期向量检索）
  → LLM 生成 1 主 + 2 备选
  → 返回建议（禁止调用任何“发送消息”企微接口）
顾问：复制 / 编辑 / 采纳 / 不适用 → event_log 埋点
```

采纳统计口径（对齐会议纪要补充）：

- `copy` 次数  
- `adopt` / `reject` / `edit_adopt`  
- 后台按顾问聚合采纳率  

### 4.4 标签模块

- MVP：`tag_def` 维护 + `customer_tag` 手工绑定 + 分布统计  
- 二期：AI 输出 `add[]` / `remove[]` + reason → 草稿推荐 → 确认后写正式绑定  
- SOP：存在 `tag_def.sop_text`，侧边栏只读展示  

### 4.5 日程模块（三期）

- Pipeline 抽时间意图 → `schedule_draft`  
- 确认后 `schedule` + 可选调用企微日历 API  
- 强/弱提醒：字段 `priority`；强提醒可用企微应用消息（若权限具备），弱提醒仅侧边栏  
- 日历同步失败时：**站内待办仍可用**（降级，非验收失败项）  

### 4.6 管理后台与角色数据范围

| 角色 | 数据范围（功能配置） |
|------|----------------------|
| 超级管理员 | 全部 |
| 区域主管 | `org_id IN 所辖` |
| 普通顾问 | `owner_user_id = 本人` |

实现：查询层统一 `apply_scope(query, user)`，避免每接口复制条件。  
说明：此为**业务可见范围**，不作为数据安全专项设计。

### 4.7 Mock 子系统（降本关键）

| Mock | 用途 |
|------|------|
| Mock 会话流 | 无企微消息权限时开发画像/话术 |
| Mock 订单 | 无订单系统时展示关联与抽取 |
| Fake LLM | 前端联调、CI、无 Key 环境返回固定 JSON |

通过环境变量 `MOCK_WECOM=true` / `MOCK_LLM=true` 切换。

## 6. 接口设计（概要）

> **详细请求/响应、错误码、SSE、时序与分期清单见 `10-接口设计文档.md`。** 以下为索引摘要。

> 统一前缀 `/api/v1`。响应 `{ code, message, data }`。鉴权：侧边栏企微换票；后台登录 JWT（常规实现，非安全专项）。**无代发消息接口。**

### 6.1 侧边栏

| 方法 | 路径 | 说明 | 阶段 |
|------|------|------|------|
| GET | /sidebar/context | 当前客户头信息+标签摘要 | MVP |
| GET | /sidebar/profile | 已确认+当前草稿 | MVP |
| POST | /sidebar/profile/generate | 触发画像生成 | MVP |
| POST | /sidebar/profile/confirm | 字段或全部确认 | MVP |
| PATCH | /sidebar/profile/draft | 手工改草稿 | MVP |
| GET | /sidebar/sse | SSE 订阅（客户维度） | MVP |
| GET | /sidebar/reply/suggest | 获取话术建议 | 二期 |
| POST | /sidebar/reply/feedback | copy/adopt/reject/edit_adopt | 二期 |
| GET/POST | /sidebar/tags… | 列表、确认推荐、手工打标 | MVP/二期 |
| GET/POST | /sidebar/schedules… | 待办与确认 | 三期 |

### 6.2 管理后台

| 方法 | 路径 | 说明 | 阶段 |
|------|------|------|------|
| CRUD | /admin/users, /admin/orgs | 员工组织 | MVP |
| GET | /admin/customers | 列表（带 scope） | MVP |
| GET | /admin/customers/{id} | 画像+沟通+订单 | MVP |
| CRUD | /admin/tags | 标签体系 | MVP |
| GET | /admin/orders | 订单 | MVP |
| GET | /admin/dashboard/summary | 漏斗/人效/续费（基础） | MVP |
| GET | /admin/ai/adoption | 采纳率 | 二期 |

### 6.3 SSE 事件约定

```text
event: profile_draft
data: {"customer_id":1,"confidence":0.82,"fields":["study_info"]}

event: reply_ready
data: {"suggestion_id":9}

event: weak_tip
data: {"text":"明日 10:00 试听回访"}
```

### 6.4 Model Gateway（内部接口）

```text
generate(task: profile|reply|tag|schedule, payload) -> StructuredResult
transcribe(audio_url) -> text   # 三期
```

默认实现：`providers/deepseek.py`（OpenAI 兼容客户端，读 `DEEPSEEK_API_KEY`）。  
其他供应商差异隔离在 `providers/openai_compatible.py` 等实现中，由 `LLM_PROVIDER` 切换。

## 7. AI 管道详细设计

### 7.1 统一 Pipeline 接口

```text
ContextLoader → PromptBuilder → LLMCaller → OutputParser → DraftWriter → Notifier(SSE)
```

每步可单测；失败时写 `event_log`/`job_error`，侧边栏提示「分析暂不可用」（可选文案，非验收硬项）。

### 7.2 Prompt 策略（控成本）

| 任务 | 上下文策略 |
|------|------------|
| 画像 | 已确认画像摘要 + 近 20～50 条消息 + 订单摘要 + 客服摘要 |
| 话术 | 已确认画像要点 + 最近 10 轮 + 场景模板 1～3 条 |
| 标签 | 已有效标签 + 标签词表 + 近窗消息要点 |
| 日程 | 近窗消息中含时间表达的片段 |

禁止把全量历史无截断塞进 Prompt。

### 7.3 结构化输出

强制 JSON Schema（FastAPI + provider json mode / 工具调用），解析失败则重试 1 次或返回可编辑空草稿。

### 7.4 异步与限流（实用主义）

- 画像/话术生成：**后台 Task（asyncio）**，先 ACK 再 SSE 推结果  
- 全局限并发（如每进程 5～10 路 LLM），超出排队  
- 不上 Celery/RabbitMQ，除非试运行后确认必要

|------|------|------|

**建议**：MVP 以 A+C 保证可交付；B 作为联调并行项，不阻塞 MVP 功能验收。

## 12. 风险与决策清单

| ID | 风险 | 影响 | 决策/缓解 |
|----|------|------|-----------|
| R1 | 企微消息能力未按时开通 | 画像无真实聊天 | Mock+手工导入；验收用演示数据路径 |
| R2 | LLM 费用超预期 | 成本 | 截断上下文、缓存确认画像、限并发 |
| R3 | 话术不符合机构风格 | 二期口碑 | 客户话术库 + 采纳反馈改 Prompt，暂缓微调 |
| R4 | 日历 API 受限 | 三期同步 | 站内待办保底 |
| R5 | 过早微服务/本地 GPU | 成本与进度 | **否决**进 MVP |
| R6 | 把安全专项写进验收 | 自埋坑 | 已从 SRS 剔除；设计亦不扩展 |

### 已拍板项

1. 前端框架：**Vue 3 + TypeScript**（侧边栏与管理后台同栈）  
2. LLM 首发供应商：**DeepSeek**（OpenAI 兼容协议；密钥环境变量 `DEEPSEEK_API_KEY`）  

### 待评审拍板项

1. MVP 是否必须打通真实企微消息，还是允许 Mock 验收（**建议允许 Mock 验收功能，联调并行**）  
2. 客服摘要数据由谁提供何种格式（CSV/API/后台录入）  
3. DeepSeek 默认模型：`deepseek-chat` 或 `deepseek-reasoner`（建议 MVP 用 `deepseek-chat`）
